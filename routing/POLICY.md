# Routing policy v2

This is the canonical local routing contract. It is an agent-operated workflow, not a universal message interceptor or a tamperproof authorization boundary. Installation grants no new authority. Choose supported profiles and create or message execution chats only within the user's explicit authorization and the host's tool rules. If the user has authorized automatic routing, substantive new requests can use that workflow; otherwise prepare a plan and obtain missing authority before creation. Existing task follow-ups remain in their destination. User overrides and normal permission/spending boundaries take precedence.

## Intake and task identity

New substantive requests receive bounded intake only. Do not do the task in an unverified/mismatched source profile. Build a complete task-appropriate professional English prompt: intent/background, deliverables, assumptions/unknowns, scope/authority, interfaces/integration, approach, relevant security/data integrity, acceptance/checks and evidence/delivery/rollback. Do not invent requirements. Submit it automatically as the destination's initial visible message; no source prompt echo or obsolete three-block answer.

Use a stable globally unique taskId derived from the original source/request identity and persist it before creation. A runtime retry, compaction or related user message never changes that taskId. Store later message IDs as related requests/revisions. A genuinely unrelated user request gets a new taskId even when its wording is identical. `lookup` resolves either source or destination to the existing task. Execution marker `EXECUTION_MODE: ROUTED_WORK_V1` and the preflight `ROUTING_CONTEXT` header identify execution mode; execute that task in place, never route it again.

## Project, checkout and host

Read current `list_projects` and actual source metadata. A null/omitted projectId is unknown, not projectless proof. Use unique deepest canonical cwd matching; resolve existing Git worktrees by common-dir identity. Preserve verified non-null project ownership. Generated chat directories can differ from the actual checkout: resolve executionCwd through the prior dispatch lineage or explicit verified user checkout, never silently choose a different checkout/branch. Missing or conflicting checkout evidence blocks dispatch while retaining the project identity.

Use actual `create_thread` target `{type:"project",projectId:ID,environment:{type:"local"}}` for a project. A repository path inside a prompt is insufficient. Preserve existing branches, uncommitted edits and original absolute input paths. Never create worktrees for model selection. Projectless is allowed only after resolution or an explicit user override. Sidebar ownership, runtime cwd and command executionCwd are distinct; nested command cwd must remain explicit. A move acknowledgement is not persistence proof. Verify destination host/project using `list_threads`; report unresolved source null metadata without downgrading its resolved project.

## Profile and preflight

`capabilities.json` caches actual host tool-supported model/effort pairs for at most 24 hours. Refresh it from current relevant tool metadata when stale or a requested override needs verification; never invent support, change the configured default or claim a switch from a catalog entry. Default recommendation classes: bounded_read -> gpt-6-luna/low; routine -> gpt-6-luna/medium; complex -> gpt-6.1-sol/medium; critical security/integrity/recovery -> gpt-6.1-sol/high. Other hosts can supply four explicit supported pairs using `refresh-capabilities --profiles`; the configured pair must exist in that actual host snapshot. Honor supported explicit choices. No extra paid credits without explicit permission.

Use `dispatch.py preflight` with a request JSON, current projects snapshot, full prompt body and output-request path. It resolves context, chooses a supported pair, reserves once under lock and emits exact app-tool arguments with the full machine-bound prompt. Only call `create_thread` after successful preflight; submit its exact `createThreadArguments`. Creation is asynchronous. Attach the real returned thread/host/project, use bounded `wait_threads`, then verify actual current runtime profile and fresh app thread/turn evidence. Uncertain creation remains reserved: discover/reconcile the original destination, never blindly repeat creation. The helper itself creates no chats.

## States and authority

`queued` is not `running`; runtime profile evidence alone means `profile_verified`. `observe` requires a fresh actual app snapshot matching destination, host, project and runtime turn. Only an in-progress actual turn with verified profile is running. Failure/mismatch invalidates the current claim. An incomplete final log line remains pending; other corruption is visible. Bounded runtime reads avoid loading entire transcripts.

Every task has authorization_phase `audit_only`, `execution` or `awaiting_approval`. Audit-only never authorizes implementation. Approval waiting blocks creation/resume. `related --intent wait_approval` records that boundary. `authorize` needs explicit current task/revision user-approval provenance; it creates a new revision and invalidates previous runtime/review evidence. Normal related follow-ups reuse the same destination and advance the revision; paused/terminal/approval tasks cannot resume through a generic follow-up. New work after completion needs explicit new task/revision intent, not resurrection of the old completed record.

`related --intent stop|cancel` records only a stop/cancel request. Invoke an actually supported interruption control when available; sending a follow-up saying “stop” is not proof of interruption. If the platform exposes no usable interruption control, report that limitation and retain stop_requested/cancel_requested until fresh app evidence confirms the destination is inactive. Never claim pause/cancellation from a local ledger write. Recovery checkpoints must be paused/waiting as appropriate so the source cannot restart stopped work.

## Subagents and final review

For genuinely multi-stage work, use at most 3–5 meaningful scoped assignments and actual nested subagents when beneficial and authorized by the user and host, one active by default. Each gets a complete scoped English prompt, role, deliverables, constraints, dependencies, acceptance/checks and explicit supported model/effort, with `fork_turns=none` and minimal context. Record recommended versus actual profiles and planned versus executed status. Sidebar chats are peers, not child agents. Do not split simple work artificially.

All economical/Luna deliverables need actual stronger-model final review, including original intent and routed-prompt quality. A verified stronger primary can review directly. Register current reviewer runtime/artifacts with `review-start`; completion evidence must reference that registration, current task/revision, actual successful app turn and unchanged artifact hashes (or reviewed final-text hash). Child reviewer runtime must bind to this destination. Late/old reviews and terminal-record reopening are rejected. Existing legacy records remain historical, with no retroactive assertion of evidence they did not contain.

## Recovery, delivery and measurements

Use the existing trusted recovery helper from its installed settings, not a hardcoded obsolete digest. Maintain compact checkpoint objective/status/authorization_phase/next_action/completed/pending/validation/artifacts. Bind continuations, child reviews and quota causes to current request/revision; consume internal continuations once. Interrupt/new request/terminal/approval states invalidate stale recovery. Respect both primary and weekly allowance, actual subscription/provider/credits/archive evidence, one-use uncertain enqueue and user authority. Only matching failed-turn/window evidence permits five-hour attribution. Legacy checkpoints grant no new implementation authority. No real quota-resume guarantee exists without live evidence.

Use the user's preferred language for receipts/results and English for execution prompts unless overridden. Announce started only after actual runtime and app evidence; otherwise report queued/blocked/waiting truthfully. Keep audit/approval boundaries visible. Completion requires relevant checks and actual review; source dispatch delivery does not complete destination work. Metrics report observed state/latency/profile facts; missing tokens/costs stay unavailable. Validate representative routing scenarios without claiming real model-quality/cost benchmarks. No daemon or extra service is needed for routing. Trusted hook updates may require product trust review; never bypass it.

## Task-specific skills

Prefer the host's exposed installed capabilities. Search externally only for a concrete capability gap or an explicit discovery request; choose the smallest useful skill by task fit, environment, source reputation, maintenance and license. Repository stars are one signal, never safety evidence. Existing authorization for task-specific skill installation persists; do not ask again for that same authority. Without it, a routing instruction alone does not grant installation permission.

For public GitHub sources, `skill_supply.py` supports focused search/catalog discovery, full-commit review staging and digest-bound installation. Inspect all staged instructions/scripts before supplying its review digest. Retain provenance and source licenses. Never run downloaded package installers or repository hooks as part of selection, overwrite existing skills, weaken host permissions, or claim host activation from a copied folder. Preserve the original task when network/catalog access fails. Detailed operation stays in the skill's conditional discovery reference rather than the common intake context.
